# Pinax · OpenDesign 路线深化提案（作者 2026-11-14 提出方向，待裁定）

> 作者原话要点：①OpenDesign 本地几乎不含原生 agent 运行时，提供充足的 tool chain 和资源包供用户选择加载；②左下角色板选设计体系风格——对照我们：不同载体不同风格、不同对标作品；③本地 pi-agent 运行时始终会落伍，子 agent 等不适合自己搞——让 DSH 的原生运行时接进来，或用别人的 CLI 嫁接，省事且用户满意；④软件可以以 DSH、WorkBuddy 的插件工作台形式存在；⑤半区＝一个设计文件（文件中心）＋多个文件会话，文件形态灵活（浏览器/草图/文档），对应我们的载体但更灵活；⑥小说本体封装到一个页面，内部实现卷/章/节，内部 HTML 设置与内置功能；工作台支持用户定制、Agent 修改、社区定制模块；后端只提供固定的本地文件绑定 API。⑦在已有的改造路径工单里，用这个思路再过一遍。

---

## 一、模型提炼：四条原则

| # | 原则 | OpenDesign 的体现 | Pinax 的对应物 |
|---|---|---|---|
| P1 | **宿主极薄** | 本地几乎无原生 agent 运行时 | 壳（AppNext/顶栏/库管理器）——P10 已开始变薄 |
| P2 | **工具链与资源包可选可载** | 色板选设计体系；功能=包 | 载体插件体系（pinax-carrier@4 四张牌）——雏形已在 |
| P3 | **文件中心＋文件会话** | 一个设计文件＋多个文件会话；浏览器/草图/文档自加自删；不需要时=清爽的产物管理中心 | 库管理器（PR-1~3）＝文件中心雏形；载体=刚性预置，缺灵活性 |
| P4 | **本体=单页工作台＋固定文件 API** | 卷/章/节内部参数＋HTML 工作台；用户/Agent/社区三层定制；后端只给固定本地文件 API | 正文还是传统三栏＋编辑器；fact 通道/writeFactFile＝固定文件 API 的第一组真实现（S1/S2 刚落） |

**一句话**：OpenDesign 把「智能」外包（运行时/工具链/风格全是可插拔的包），把「地基」做硬（文件中心＋固定文件 API）。Pinax 的插件体系方向本来就对，但**运行时还握在自己手里**、**文件形态还是预置刚性**——这两点是要深化的。

---

## 二、关键判断：运行时外包是顺势，不是退让

作者已经在自己的工作流里验证了这条路：**Qoder／CodeBuddy／Claude CLI 一直在当实现工人**（P1~P10 全是他们做的），派单管线（dispatch-qoder/codebuddy-wf.mjs）就是「外部 CLI 嫁接」的活证。产品侧同样的道理：

- **pi-agent 运行时永远会落伍**：模型迭代、子代理编排、工具生态——自己追成本无限。
- **DSH 原生运行时**：作者自有产品，接口可控（右栏开放＋外部插件 services 解禁＝进程即沙箱，已有裁定）。
- **别人的 CLI**：Claude Code／CodeBuddy／Qoder——沙箱即进程，凭据归用户。
- Pinax 保留的应是：**会话集 UI＋文件绑定 API＋提案/审计闸**（writeFactFile 那套）——这些是 Pinax 的差异化，不外包。

## 四、深化路线（R 系批次建议）

| 批 | 内容 | 依赖 | 规模 |
|---|---|---|---|
| **R0 地基**（已完成的就不重复） | fact 四通道＋writeFactFile＋库管理器＋顶栏薄壳 | — | ✅ S1/S2/P10 已落 |
| **R1 运行时端口** | 定义 Runtime Port 契约（ask/complete/stream/abort/sessions/tools/events——从现有 RuntimeDock↔pi 运行时的真实调用面反推）；pi-agent 运行时改成端口的**参考实现**；RuntimeDock/左列改读端口 | R0 | 中大 |
| **R2 外部运行时嫁接** | DSH 运行时适配器（需作者给 DSH 接口规格）＋CLI 适配器（CodeBuddy/Claude/Qoder，进程即沙箱）＋**运行时选择器 UI**（左下角色板位：本地 pi / DSH / 外部 CLI） | R1 | 中 |
| **R3 风格包（色板）** | 载体级设计体系包（对标作品的 token 集合：色/字/圆角/密度）＋左下角色板 UI；P6 的珊瑚红就是第一个包 | R0 | 小中 |
| **R4 文件中心会话化** | 库内文件级会话：用户自加 pane 形态（浏览器/草图/文档/内置载体），删了即清爽；载体从「预置 12 块」变「可选包＋自加文件」 | 库管理器 | 中大 |
| **R5 小说单页工作台** | 正文单页封装（卷/章/节内部参数）＋HTML 工作台＋定制 API（用户改/Agent 改/社区模块装载）；后端只有文件绑定 API | S1/S2（已完成）＋R4 | 大 |
| **S5 任务队列** | 运行时无关的作业 runner（拆解/派生/长任务），进度走 IPC_PUSH | R1 | 中 |

**排期建议**：R1（端口）是唯一的新地基，先做；R3 色板小而显眼可插队；R2 等 DSH 规格到手；R4/R5 在 R1 后排。

## 五、要作者裁定的三件事

1. **pi-agent 运行时的地位**：降为「参考实现」（保留维护、保证零配置可用）还是逐步退役？——影响 R1 的适配器设计深度。
2. **DSH 接口规格**：R2 的 DSH 适配器需要 DSH 侧的接口文档（作者提供或授权我去读 DSH 源码）。
3. **R 系与 S0-S5 的关系**：拆解主线（S5 任务队列之后）是否暂停让位 R 系，还是双线并行（S 线后端、R 线前端不同文件可并行）。

## 六、风险与诚实边界

- **运行时外包≠零维护**：端口契约本身要维护；外部 CLI 的凭据/速度/质量归用户自己的账号。
- **DSH 规格未知**：R2 的工期估算在拿到接口前都是猜的。
- **社区模块**：分发形态（目录导入/在线市场）没定之前，R5 的「社区定制」只到「本地装载」这一步。
- **本提案未动任何代码**——纯路线文档，等作者拍板后按 R 系开工单。
