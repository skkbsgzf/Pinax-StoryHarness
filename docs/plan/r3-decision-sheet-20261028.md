## 2. R3-a：迁哪些、不迁哪些

| 类目 | 建议 | 落到 | 理由 |
|---|---|---|---|
| 正文（books→章节） | **迁** | `正文/NNN-标题.md` | 作者的真稿，唯一不可丢的东西 |
| 构思 / 人物 / 场景 / 时间线 | **迁** | `构思/`、`世界书/`（人物）、`大纲/`（时间线→大纲节点） | 都是创作素材，Next 已有对应面与工具 |
| 世界地图 / 世界设定 | **迁**（设定部分） | `世界书/` | 地图渲染（canvas）Next 未做，数据先迁、UI 后补 |
| 媒体二进制（`pinax-media`） | **迁** | `assets/`（二进制原样拷贝） | 图片是作者的资产；Next 已有 `media.assets` capability 词条 |
| 资料长文（`pinax-source-archive`） | **迁** | `资料/` | 对应面已存在（只读为主） |
| 体验会话（`writing_sessions`） | **暂不迁** | — | 体验载体在 M5；迁进来也没有面承载 |
| 排版偏好 / 活动时间 / 小状态 | **不迁** | Next 偏好文件（`next-preferences.json` / `app_theme`） | 老轨排版面（ProseMirror）尚未迁入；Next 已有自己的偏好面 |
| 事实账本（`ledgerDb`） | **只读归档** | `.pinax/state/legacy-ledger.json`（导出原样） | Next 无对应面；先存证，不猜语义 |

## 3. R3-b：修订史怎么处置（**这是最需要你拍的一条**）

事实：老前端 `revisions` 仓存的是**每版正文快照**（`before`/`after` 全文）；Next 的 `expectedRevision` 是**文件级并发号**（防覆盖用），**不保留历史**。所以「迁修订史」不是搬文件，而是选择：

| 选项 | 做法 | 代价 | 你得到的 |
|---|---|---|---|
| **B1（推荐）** | 一次性导出为只读存档：`.pinax/state/revisions/<文件名>/<版号>.md` | 一次性脚本（约半天），占磁盘（每版全文） | 历史一版不丢；Next UI 本批不读它，将来「历史对比」有料可用 |
| B2 | 不迁，只保当前正文 | 零成本 | 旧版正文永久丢失（浏览器数据还在，但 Next 里没有） |
| B3 | 迁 + Next UI 做「历史」面板 | 脚本 + 一个新设置节（约 2 批） | 体验最完整，但排在功能迁移之后 |

## 4. R3-c：时机与老存储的处置

| 项 | 建议 | 说明 |
|---|---|---|
| 时机 | **一次性导入**（脚本跑一次，产出 `.pinax/` 全量） | 不做双轨实时同步（最贵、最容易撕票） |
| 冲突 | 导入前要求目标目录为空；已存在 `.pinax/project.json` 的走「合并计划 dryRun」 | 复用 `pinax_project_import` 的既有语义（默认 dryRun、源只读） |
| 老存储 | **留备份不删**（浏览器 localStorage/IndexedDB 原样留着） | 作者的原稿永远比代码活得久（C4 同口径）；Next 只读不写老存储 |
| 验收 | **双跑核对**：《大梦》导入后章数/字数/条目数三方一致（老 web 读出 vs Next 读出 vs 源文件） | 规范 §9 DoD 第 7 条 |
